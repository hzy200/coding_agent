## 第一部分 · 现状评估

### 1.1 评估尺度

同一个项目在两个尺度下评价截然相反，必须先校准：

| 尺度 | 评价 |
| --- | --- |
| 作为毕业设计 | **顶级**。安全纵深、审计完整性、可回滚性、测试密度、文档纪律均远超毕设常态 |
| 作为"高性能自主编码智能体" | **原型阶段**。工程底座接近生产，能力面覆盖约 40% |

本文档按**后者**评估。

### 1.2 成熟度基线（六维度）

| 维度 | 目标要求 | 现状 | 完成度 |
| --- | --- | --- | --- |
| 执行与安全底座 | 可控、可审计、可回滚 | 六层纵深、判定权在宿主、fail-closed 一致 | **90%** |
| 代码修改机制 | 精确、可回滚 | 精确替换 + diff + 写前备份 + 回滚可回滚 | **70%** |
| 代码理解 | 结构化理解仓库 | 纯词法检索（rg/grep） | **25%** |
| 自主工作流推进 | 计划可修正、目标驱动 | 一次性静态计划 + 硬上限修复循环 | **35%** |
| 结果可信度 | 产出经过独立验证 | 只认测试命令；无测试即无验证 | **35%** |
| 运行时性能 | 高频交互可用 | 每次操作 2–4 次进程启动，无缓存、无并行 | **25%** |
| 效果可度量 | 能证明能力提升 | 无任务级评测 | **5%** |

**核心矛盾**：**工程成熟度远高于目标完整性**。底座（安全、审计、回滚、测试、模块边界）
比大多数同类项目扎实，缺的是上层能力栈——而这两者的**返工成本恰好相反**。

### 1.3 已建成的、难以返工的资产（本次评估要保护的对象）

以下六项是**架构定型后几乎无法补做**的，它们已经完成且有测试守着：

1. **安全判定权完全在宿主**（`sandbox/policy.py`），不依赖模型自我申报；
   引号感知已打磨到 `$'...'`、嵌套 `$()`、`sh -c` 包装层。
2. **决定与执行分离**：`approval_gate` 纯函数 + `tools` 节点唯一咽喉（`graph/nodes/`）。
3. **审计写失败宁可让运行失败**，不静默丢记录（`audit/logger.py`）。
4. **回滚本身可回滚**（`sandbox/snapshots.py:153-205`）。
5. **分层边界由 AST 测试强制**（`tests/unit/test_architecture.py`）：
   `tui`/`web` 导入 `tools`/`sandbox` 直接失败。
6. **测试网 + 扩展点文档化**：加工具/加节点是 3–4 步的机械操作，见 README「想改什么，看哪里」。

**结论：差距的形状是「可填充」，不是「要推倒」。** 本计划全程不触碰上述六项。

### 1.4 性能基线（实测，可复现）

用探针统计 `WslSandbox.run` 调用次数得出，非估算：

| 项 | 上一版声称 | **实测** | 备注 |
| --- | --- | --- | --- |
| 冷启动 `wsl.exe` 次数 | 9 | **4** | `$HOME` → memory stat → 工作区 realpath → `rg` 探测 |
| 冷启动延迟 | ≈2.7s | **≈1.2s** | 按每次进程启动 0.2–0.3s |
| `file_read` | 2 | **2** ✓ | `resolve` + `read_text` 各一次 |
| `file_edit` | 4–5 | **4** ✓ | resolve + read + 备份写 + 写入 |
| 单次验证 | 2 | **2** ✓ | 命令探测 + 执行（外加一整轮测试） |
| 工具并行度 | 1 | **1** ✓ | `graph/nodes/tools.py:117` 串行 |

**「9 次」错在哪**：它数的是 `resolve_workspace` 的**调用点**，忽略了
`runtime.effective_settings`（`runtime.py:265-273`）会把已解析的工作区**写回配置**，
而 `build_graph` 收的正是这份配置 —— 于是 `wsl_exec.py:282-284` 的非空分支短路了，
六个工具构造器一次 `$HOME` 都不探。**任何按原始 settings 调 `build_tools()` 的新前端
才会重新踩到那 9 次**，所以缓存仍值得做，但理由是去掉隐式依赖，不是省 2.1s。

## 第二部分 · 缺陷分析

### P0 · 阻断目标达成的结构性缺陷

| # | 缺陷 | 位置 | 为什么是 P0 |
| --- | --- | --- | --- |
| **P0-1** | **planner 开环：执行中无法重规划** | `graph/build.py:106-107` | **自主性天花板**。没有任何边指回 planner，`advance` 只递增 `step_idx`。"第 2 步发现计划错了"的唯一结局是继续走完过时计划。当前架构更准确的描述是**"一次规划 + 固定清单执行器"**，不是自主智能体 |
| **P0-2** | **验证在无测试项目上静默失效** | `tools/testrun.py:254-258` → `graph/routing.py:48-58` | 追踪全路径：识别不出测试命令 → `not_configured` → 路由判为非 failed → 直接 `advance` → `runtime.py:816-822` 记成 `ok=True`。**在没有测试的项目上，整条验证脊柱静默失效**，产出代码没有任何独立质量判断 |
| **P0-3** | **评测集无区分度：一切改进仍不可证** | `tests/eval/` | harness 已建成且可信（双向自检），但 26 个任务实测 **26/26 = 100%**（basic 20/20、deep 6/6），平均只用 17% 工具预算。**它现在是回归护栏，不是能力尺子** —— 测不出提升。要能测，需要规模上的量级变化（几百文件的仓库、几十步的任务、模糊需求、跨会话长程），而非把谜题设计得更刁钻。详见 §3.2 的 W1 记录 <br>**2026-10-06 复核**：任务集已扩到 **29 个**（20 basic + 9 deep，其中 3 个来自 `tasks_replan.py`），沙箱里也有了 pytest —— 自动验证与修复循环首次真正生效，最新基线 **18/29 = 62%**，已落在本节要的 30–70% 区间。所以「无区分度」的诊断**不再准确**；真正还缺的是**动态范围的上端**（最大任务仅 9 文件 / 68 行，`tool_calls` 中位数约 7，预算 60）。同时补齐了两件度量前提：**机制指标**（验证/修复/重规划次数、token，回答「那条回路真的被走过吗」——`--ab` 那次误读正是缺它才发生的）与**噪声地板**（`--repeat k`，29 个任务翻一个是 3.4 个百分点）。另加可比性守卫：子集 / 脏工作区 / 无 pytest 时拒绝写基线 |
| **P0-4** | **上下文只截断不压缩，且 state 无界增长** | `llm/context.py:154-188` | 裁剪只作用于**发给模型的消息**（`act.py:72`），不改 `state.messages`。后果双重的：长任务里模型在最需要理解力时被截断了刚读进来的代码；同时 checkpoint 只增不减，`trim_messages` 每轮 O(n) 全量扫描 → O(n²) 累积 |

**本次已修复（记录在案）**：`estimate_recursion_limit` 漏算 repair 循环 —— `repair`
会把 `tool_rounds` 清零，每轮修复重新吃满一个完整周期，而公式只按单周期推导，
导致走了修复路径的任务以 `GraphRecursionError` 收场、拿不到"试过但没修好"的收尾。
已改为 `(修复次数+1)×周期`，并补图级回归用例（`tests/unit/test_repair.py`）。
**教训**：**新增图节点必须同步更新该公式** —— 这是它第二次算歪，replan 落地时会再碰一次。

### P2 · 性能与吞吐

**先校准优先级**：一次 30 次工具调用的任务，进程启动开销约 **8 秒**，
而同期 LLM 墙钟通常是**几分钟**量级 —— **I/O 是总时长的 5–10%，不是瓶颈**。
真正的墙钟成本是"需要多少轮 LLM 往返"，由**理解质量与规划质量**决定。
因此 P2 是**体验问题**，不是能力问题；排期上放在最后（例外见 P2-5）。

- **A1**：空字符串是 `count` / `replace` 的特例 —— **凡是用计数做唯一性判断的地方，
  都要给输入显式设下限**（`min_length=1`），靠「出现 0 次 / 多次就拒绝」的逻辑挡不住空串。
- **A2**：**安全属性测试自身也需要防绕过用例**。只比对绝对模块名会被
  `from ..sandbox import x`（`node.level != 0`）与 `from pkg import sub` 两种常见写法绕过 ——
  这种洞给出的虚假保证比没有测试更危险。
- **A4**：「有结构化产物」不等于「产物语义正确」。拒绝路径原先是所有工具共用一个

  契约测试必须同时覆盖「声明了就必须发」这个方向。

  这也说明「契约缺失」与「前端状态残留」常常是同一个问题的两面。

### 3.1 排期原则（本版修订）

1. **先建评测，再改能力。** 没有 benchmark 就无法证明自主性真的提升了 —— 这是唯一客观依据。

4. **不改安全模型。** 六层纵深是最强资产，本轮不动 `policy.py` 判定逻辑。

   能力栈补齐前拆分只会让每次加节点都要改三个文件。P3-1 中的**补测试**（P1-11）优先于**改结构**。

## 第五部分 · 明确不做（范围边界）

为避免三个月内失焦，以下**明确排除**：

- **不改安全模型。** 六层纵深是当前最强资产，本轮不动 `policy.py` 判定逻辑。
  —— A6（只读会话的提示词与 UI 标签「说反话」）因此**只改描述、不改判定**：
  让提示词、侧栏标签与 `SessionPolicy` 的实际行为对齐，而不是把 L2/L3 改成 DENY。
- **不重构 `runtime.py`。** 推迟到 M3′ 之后；本轮只补它缺的测试（P1-11），不动结构。
- **不引入多模型路由 / 不换 LLM Provider。** 单模型足以验证能力栈。
- **不做语义检索（向量 / Embedding）。** 收益不确定且引入新依赖，符号索引已覆盖主要诉求。
- **不做编辑器插件 / IDE 集成。** TUI 是主要界面，Web 保持"最小验证"定位。
- **不做 P3 全量清理。** P3-2/P3-3/P3-4/P3-10 顺路做（在对应周次已排），其余攒到 M3′ 后统一处理。

## 第六部分 · 结论

当前项目是一个**工程底座达到准生产水准、能力栈处于原型验证阶段**的自治智能体骨架。

它已经证明了三件事：**安全可信的自主编码循环走得通**、**精确可回滚的代码修改可实现**、
**失败驱动的修复循环有价值**。这三个是同类系统里最难做对的部分，而它们已经完成且被测试守住 ——
更重要的是，它们恰好是**架构定型后几乎无法补做**的部分。

> **一处诚实的限定**：「被测试守住」目前只在**本地**成立 —— CI 跑不到沙箱层，
> 那约 11.6 个百分点的覆盖（全量 90.49% → CI 子集 78.87%）只靠人记得手动跑 `-m wsl`。
> 覆盖率门槛已设为 **76**（见 **Q1**），它能拦住「快反馈部分整体退化」，
> 但**拦不住「沙箱层悄悄坏掉」**—— 这正是 Q1 收尾项要补上的。

距离"高性能自主编码智能体"，缺的是三件事，且顺序不能颠倒：

1. **可度量性**（1 个月）—— 没有评测，后面每一项改动都无法验证，所有"提升"都只是宣称
2. **自主闭环**（1 个月）—— 计划可修正 + 上下文不丢失，这是"自主"二字的实际含义
3. **理解与可信**（1 个月）—— 符号级结构理解决定任务复杂度上限；多重验证决定产出可信

**性能排在这三者之后**：实测显示 I/O 开销只占总墙钟的 5–10%，真正的成本是"需要多少轮 LLM 往返"，
而它由理解质量与规划质量决定。把性能排在能力之前，是拿体验优化换取天花板的推迟。

三个月后若三个阶段全部达成，项目将从"**安全的原型**"升级为
"**能力完整、过程可度量、性能达标的可演示自主编码智能体**" —— 且由于全程有评测集与基准套件，
每一分提升都是可量化、可证明的。
