# RFC-NNNN：标题

> 一句话说明要解决什么问题、为什么现在做。

## 1. 目标

- 可验证的目标（完成后能用哪条测试/命令证明）。

## 2. 非目标

- 明确不做什么。没有非目标，范围就会在实现中膨胀。

## 3. 背景与证据

- 触发原因：缺陷、事故复盘、评测数据、用户需求；
- 相关 issue / postmortem / ADR / eval 结果；
- 当前行为与期望行为的差距。

## 4. 受影响面

| 项 | 内容 |
|---|---|
| 模块 | `graph/`、`orchestrator/`…… |
| 契约 | 事件 / 配置 / 工具等级 / 审计字段是否变化 |
| 数据 | 是否需要迁移、兼容窗口、回滚方式 |
| 前端 | CLI / TUI / Web 是否需要同步 |
| 权限 | 是否触及审批、沙箱、路径守卫、密钥 |

## 5. 安全与隐私

- 对照 [`../THREAT_MODEL.md`](../THREAT_MODEL.md)：新增哪类资产、对手或攻击面；
- 哪些操作需要人工批准；哪些日志/审计字段必须脱敏。

## 6. 兼容与回滚

- 破坏性变更：无 / 有（说明迁移与弃用窗口）；
- 回滚方式：配置开关、版本回退、快照恢复、数据库回滚；
- 回滚是否也可回滚。

## 7. 可观测性

- 新增或修改的事件、审计记录、指标、告警；
- 失败时如何从审计/日志判断“做到哪一步”。

## 8. 验收标准

用 Given-When-Then 写，至少一条能直接转成测试：

```text
Given ...
When  ...
Then  ...
```

验收锚点写入 [`../acceptance/acceptance-criteria.yaml`](../acceptance/acceptance-criteria.yaml)，
并链接到 `tests/...::test_name`。
