# ADR-0003：配置优先级刻意让 `.env` 高于环境变量

- **Status**：accepted · 事后补录
- **Date**：2026-10-22
- **Owner**：项目作者
- **Tags**：配置 · 与通用约定的刻意偏离

## Context

业界通用约定是「环境变量 > `.env` 文件」。照做之后踩到一个真实故障：

某些工具链会在**进程启动时**往环境里注入变量。用户既看不到来源
（不在注册表、也不在任何配置文件里）也删不掉，于是改 `.env` 完全不生效，
表现为「明明更新了 API key 却一直 403」。这类问题排查成本极高，
因为从用户视角看，配置文件里写的是对的。

## Decision

优先级定为：**构造函数参数 > `.env` > 环境变量 > 默认值**。

理由：项目目录里的 `.env` 是**显式写下、看得见、可编辑**的意图，让它优先；
需要临时覆盖时用命令行前缀，或去改 `.env` 本身。

配套：`_NonEmptyDotEnvSource` 让 `.env` 里的空占位（`KEY=`）不算"配置过"——
否则从 `.env.example` 复制来的空行会盖掉环境变量里真正可用的值。

## Consequences

### 好的

- 消灭了"改了配置文件却不生效、且看不出为什么"这一类最难排查的故障；
- 显式覆盖仍然可用（构造函数参数最高优先），测试与嵌入式用法不受影响。

### 坏的 / 代价

- **偏离通用约定**，第一次接触的人会以为配错了；
- 环境变量覆盖失效，某些 CI/容器注入的用法需要改成写 `.env`。

### 中性 / 需要留意

- 缓解措施：`agent doctor` 会列出两边不一致的键并给出 WARN，
  明确写出"当前生效的是 .env 里那份"。**这个提示是本决策的一部分，不要删。**

## 复核

- **Verified by**：`pytest -m "not llm" tests/unit/test_config_sources.py tests/unit/test_instructions.py`
- **Revisit when**：配置加载顺序或 .env 注入方式变化时

若有用户报告"在容器里用环境变量部署，改不了"且 doctor 提示不足以定位，
再考虑增加显式的 `--env-source` 开关——而不是改回通用优先级。
