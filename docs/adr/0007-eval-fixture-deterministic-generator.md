# ADR-0007：长程评测仓库用确定性生成器，不用真实仓库

- **Status**：accepted（**刻意偏离原计划**）
- **Date**：2026-10-22
- **Owner**：评测维护者
- **Tags**：评测 · 与计划的刻意偏离

## Context

`IMPROVEMENT_PLAN §3.2 W2` 的风险对策写的是「任务源自真实仓库而非自造」。
这条对策真正要防的是两件事：**任务太简单**，以及**任务与实现耦合**。

但直接用真实仓库会带来四个新问题：

| 问题 | 说明 |
|---|---|
| 可复现 | 真实仓库会变（上游提交），同一份规格跑不出同一份结果 |
| 零依赖 | 判定不能被第三方的 requirements 绑架（沙箱里没有 pip） |
| 问题位置不可控 | 要测的是「在几十个文件里定位并贯通修改」，问题的位置必须是我们设计的 |
| 体积 | 38 个文件进库会让 diff 淹没真正的改动 |

## Decision

用**确定性生成器**：进库的是几百行生成器，不是几十个文件。
同一份规格永远生成同一份仓库（含固定时间戳的初始提交）。

- 规模：**38 个文件 / 约 970 行**，分层（模型 / 仓储 / 校验 / 服务 / 报表 / 12 handler / 9 util / 3 adapter）；
- 生成器只产"健康"仓库，每个任务用 `patch()` 注入功能缺口；
- **`patch()` 要求锚点恰好出现一次**——模板改了而功能线没跟着改时补丁会静默失效，
  这条断言是整个生成方案的结构性保障（`test_eval_harness.py` 有对应用例）；
- 6 个任务按**形态**补，不复制同类任务（2 个任务的样本下任何调参实验都无法评估）。

## Consequences

### 好的

- 可复现、零依赖、体积可控、问题位置可控；
- 由**规模**挡住「任务太简单」（38 文件定位本身就要十几次工具调用）；
- 由既有的两条判定原则挡住「与实现耦合」（只看外部可观察结果 + 判分前纯净副本覆盖测试）。

### 坏的 / 代价

- **不是真实仓库**：可能缺少真实项目的脏乱（历史包袱、不一致的命名、残缺的文档）；
- 生成器的 bug 会系统性影响所有长程任务；
- 偏离了原计划的风险对策，需要显式说明（就是本文件）。

### 中性 / 需要留意

- `long` 套件波动很大（历史 2/5 = 30%，spread 20pp），结论必须超出 spread 才值得讨论。

## 复核

- **Verified by**：`pytest -m "not llm" tests/unit/test_eval_harness.py tests/unit/test_full_task_catalog.py`
- **Revisit when**：长程任务模板或真实仓库评估需求出现时

若后续要测「在脏乱的真实仓库里工作」，应**新增**一个真实仓库套件，
而不是替换掉确定性生成器——可复现性是基线可比的前提。
